# ТвойВыбор.exe — backend

Основа монолитного API на FastAPI. `GET /health` возвращает `{"status":"ok"}`
после успешного запроса к PostgreSQL или HTTP 503, если база недоступна.
На этапе 1 добавлены пользовательская схема и авторизация.

## Локальный запуск

Общий Docker Compose находится в соседнем репозитории
`../tvoyvybor-frontend/docker-compose.yml`. Его инструкция запуска описана в
README frontend-репозитория. В backend контейнер передаются `DATABASE_URL`,
`JWT_SECRET`, `CORS_ORIGINS` и `APP_ENV`; образ собирается из этого каталога.

Для отдельного запуска скопируйте `.env.example` в `.env`, укажите действующие
параметры локальной PostgreSQL и выполните:

```sh
python3 -m venv .venv
. .venv/bin/activate
pip install '.[dev]'
set -a; . ./.env; set +a
alembic upgrade head
uvicorn app.main:app --reload
```

Проверка: `curl http://localhost:8000/health`.

## Проверки качества

```sh
ruff format --check .
ruff check .
pytest
```

Миграция `0001_stage_0` создаёт историю Alembic, `0002_users` — таблицу
пользователей, `0003_content_game_core` — направления, сценарии, задания и
прогресс. Compose выполняет `alembic upgrade head` перед запуском API.

## Аутентификация этапа 1

API принимает JSON. `POST /auth/register` с `{"email":"user@example.com",
"password":"password123"}` возвращает HTTP 201 и `id`, нормализованный
`email`, `role: "user"`. Пароль: 8–128 символов; дополнительные поля (в том
числе `role`) отклоняются. Повторный email возвращает 409.

`POST /auth/login` принимает те же поля и возвращает HTTP 200 с
`access_token` и `token_type: "bearer"`. Неверные учётные данные дают 401.
`GET /auth/me` требует заголовок `Authorization: Bearer <access_token>` и
возвращает `id`, `email`, `role`; отсутствие или недействительность токена дают
401. Access JWT подписывается HS256 секретом `JWT_SECRET` и действует 1 час.
Refresh token на этом этапе не нужен. Пароли хранятся в виде PBKDF2-SHA256
с индивидуальной солью; публичная регистрация всегда присваивает роль `user`.
Роль `admin` проверяется на сервере по текущей записи пользователя в БД.
Выдача роли администратору через пользовательский API не предусмотрена на
этом этапе; отдельный порядок назначения нужен перед внедрением admin UI.

В ТЗ не зафиксированы точные поля и статусы auth API; этот минимальный контракт
принят для этапа 1. Интерфейс авторизации React появится на этапе 4 roadmap.

## Контент и прогресс этапа 2

Все маршруты требуют Bearer JWT. Администратор создаёт направление через
`POST /admin/directions` с `slug`, `title`, `description`; сценарий через
`POST /admin/scenarios` с `direction_id`, `slug`, `title`, `description`; задание
через `POST /admin/scenarios/{id}/tasks` с `kind`, `title`, `content` (JSON-объект),
`validation_config` (JSON-объект), `correct_explanation` и
`incorrect_explanation`. Задания и сценарии изначально
являются черновиками. Для публикации сначала вызвать
`PUT /admin/tasks/{id}/publish`, затем `PUT /admin/scenarios/{id}/publish`.
Для публикации сценария требуется хотя бы одно опубликованное задание. Повторные
запросы публикации безопасны. После публикации сценария новые задания в нём
нельзя опубликовать: список заданий остаётся фиксированным для расчёта завершения.
Операции `/admin` требуют роли `admin` в базе данных.

Игрок читает `GET /directions`, `GET /scenarios` (необязательный фильтр
`direction_id`), `GET /scenarios/{id}` и `GET /progress`. Списки сценариев и
детали показывают только опубликованный контент; задания-черновики скрыты.
Проверочная конфигурация и объяснение ответа доступны только администратору.
`PUT /scenarios/{id}/start` переводит опубликованный сценарий из доступного
состояния в `active` и возвращает сохранённый статус. Повторный вызов для
`active` идемпотентен. Прогресс хранится отдельно для каждого пользователя.

Enum прогресса содержит `locked`, `available`, `active`, `completed`, `skipped`.
Новый опубликованный сценарий считается `available` без записи в БД; сохранённый
статус `available` также может перейти в `active`. На этапе 2
разрешён переход `available → active`; этап 3 добавляет `active → completed`.
Клиент не может перевести `locked` в другое состояние. Пропуск пока не
используется. Этот API пока поддерживает только создание и публикацию контента;
редактирование и снятие с публикации запланированы на этап 7.

## Попытки и профиль этапа 3

Первый поддержанный тип задания — `choice`. Его `validation_config` содержит
`{"correct": "точная строка ответа"}`. Для ручной проверки можно создать пять
опубликованных заданий одной командой после миграций:

```sh
cd ../tvoyvybor-frontend
docker compose build backend
docker compose run --rm backend python -m scripts.seed_stage3
```

Команда повторяема: уже созданные задания не дублируются. Она не создаёт
пользователей и не выдаёт права администратора.

Игрок регистрируется, начинает опубликованный сценарий через
`PUT /scenarios/{id}/start`, затем отправляет
`POST /tasks/{id}/attempts` с JSON `{"request_id": "UUID", "answer": "GET"}`.
`request_id` создаётся клиентом один раз на логическую отправку и повторно
используется при сетевом повторе; тот же ID с другим содержимым даёт HTTP 409.
Ответ HTTP 201 содержит `id`, `task_id`, `is_correct`, `reaction` (`retry` или
`completed`), `explanation` и `scenario_state`. Неверный ответ можно повторить
без ограничения числа попыток. После первого верного ответа задание считается
выполненным; повторное выполнение с новым ID отклоняется с 409. Сценарий
завершается, когда верно выполнены все его опубликованные задания.

Каждая попытка сохраняется с серверным результатом, временем и событием
интереса. Неверный ответ даёт событие веса 0, первый верный ответ — событие
веса 1 по направлению сценария. `GET /interest-events` возвращает эти события;
`GET /interest-profile` — суммы весов по направлениям и число верно выполненных
заданий. `GET /recommendation` возвращает сохранённое направление с наибольшей
суммой и кратким объяснением либо `null` до первого верного ответа. При
равенстве выбирается направление с меньшим ID. `GET /achievements` показывает
достижение за первое верно выполненное задание. Все эти маршруты требуют JWT
и отдают только данные текущего пользователя. Попытка и её последствия
сохраняются одной транзакцией. XP и пропуск в этой версии не начисляются.
