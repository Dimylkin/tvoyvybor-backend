# ТвойВыбор.exe — backend

Основа монолитного API на FastAPI. `GET /health` возвращает `{"status":"ok"}`
после успешного запроса к PostgreSQL или HTTP 503, если база недоступна.
На этапе 1 добавлены пользовательская схема и авторизация.

## Локальный запуск

PostgreSQL запускается отдельно в Docker из соседнего frontend-репозитория;
инструкция и выбор Compose project описаны в его README. Подготовьте Python
3.12+ и окружение, не перезаписывая существующие `.venv` и `.env`:

```sh
python3 -m venv .venv  # только если окружения ещё нет
.venv/bin/pip install -e '.[dev]'
cp .env.example .env  # только если файла ещё нет
```

Настройте `.env`: `DATABASE_URL` должен указывать на нужную базу через
`127.0.0.1:5433`, логин и пароль должны совпадать с инициализированной базой
(специальные символы в URL кодируются). `JWT_SECRET` должен совпадать с
используемым ранее секретом, чтобы существующие токены оставались действительны;
для новой базы задайте случайный секрет. `.env` — shell-файл: заключайте
значения со специальными символами в кавычки и не добавляйте исполняемый код.

Проверьте выбранную базу и состояние миграций перед изменением схемы. Для новой
базы или после проверки примените миграции отдельно и запустите API:

```sh
make dev-migrate
make dev-start
```

Команды используют `.venv` и `.env`; запуск API не применяет миграции и не
запускает frontend или Docker. Остановите его через Ctrl+C. Проверка:
`curl http://127.0.0.1:8000/health` (503 означает недоступную БД). При ошибке
подключения проверьте Compose project, порт, учётные данные и состояние db;
при отсутствии конфигурации или зависимостей команда сообщит, что подготовить.

## Аутентификация этапа 1

API принимает JSON. `POST /auth/register` с `{"email":"user@example.com",
"password":"password123"}` возвращает HTTP 201 и `id`, нормализованный
`email`, `role: "user"`. Пароль: 8–128 символов; дополнительные поля (в том
числе `role`) отклоняются. Повторный email возвращает 409.

`POST /auth/login` принимает те же поля и возвращает HTTP 200 с
`access_token` и `token_type: "bearer"`. Неверные учётные данные дают 401.
`GET /auth/me` требует заголовок `Authorization: Bearer <access_token>` и
возвращает `id`, `email`, `role`, `onboarding_completed`, `intro_completed` и
`main_story_completed`; отсутствие или
недействительность токена дают 401. `PUT /auth/me/onboarding-complete` с тем же
JWT идемпотентно отмечает вступление в кампус просмотренным. Access JWT
подписывается HS256 секретом `JWT_SECRET` и действует 1 час.
Refresh token на этом этапе не нужен. Пароли хранятся в виде PBKDF2-SHA256
с индивидуальной солью; публичная регистрация всегда присваивает роль `user`.
Роль `admin` проверяется на сервере по текущей записи пользователя в БД.
Выдача роли администратору через пользовательский API не предусмотрена на
этом этапе; отдельный порядок назначения нужен перед внедрением admin UI.

В ТЗ не зафиксированы точные поля и статусы auth API; этот минимальный контракт
принят для этапа 1. Интерфейс авторизации React появится на этапе 4 roadmap.

## Контент и прогресс этапа 2

Все маршруты требуют Bearer JWT. Администратор создаёт направление через
`POST /admin/directions` с `slug`, `title`, `description`; сценарий через
`POST /admin/scenarios` с `direction_id`, `slug`, `title`, `description`; задание
через `POST /admin/scenarios/{id}/tasks` с `kind`, `title`, `content` (JSON-объект),
`validation_config` (JSON-объект), `correct_explanation` и
`incorrect_explanation`. Задания и сценарии изначально
являются черновиками. Для публикации сначала вызвать
`PUT /admin/tasks/{id}/publish`, затем `PUT /admin/scenarios/{id}/publish`.
Для публикации сценария требуется хотя бы одно опубликованное задание. Повторные
запросы публикации безопасны. После публикации сценария новые задания в нём
нельзя опубликовать: список заданий остаётся фиксированным для расчёта завершения.
Операции `/admin` требуют роли `admin` в базе данных.

Игрок читает `GET /directions`, `GET /scenarios` (необязательный фильтр
`direction_id`), `GET /scenarios/{id}` и `GET /progress`. Списки сценариев и
детали показывают только опубликованный контент; задания-черновики скрыты.
Проверочная конфигурация и объяснение ответа доступны только администратору.
`PUT /scenarios/{id}/start` переводит опубликованный сценарий из доступного
состояния в `active` и возвращает сохранённый статус. Повторный вызов для
`active` идемпотентен. Прогресс хранится отдельно для каждого пользователя.

Enum прогресса содержит `locked`, `available`, `active`, `completed`, `skipped`.
Новый опубликованный сценарий считается `available` без записи в БД; сохранённый
статус `available` также может перейти в `active`. На этапе 2
разрешён переход `available → active`; этап 3 добавляет `active → completed`.
Клиент не может перевести `locked` в другое состояние. Пропуск пока не
используется. Этот API пока поддерживает только создание и публикацию контента;
редактирование и снятие с публикации запланированы на этап 7.

## Попытки и профиль этапа 3

Первый поддержанный тип задания — `choice`. Его `validation_config` содержит
`{"correct": "точная строка ответа"}`. Для ручной проверки раннего среза можно создать пять
опубликованных заданий одной командой после миграций:

```sh
cd ../tvoyvybor-frontend
docker compose build backend
docker compose run --rm backend python -m scripts.seed_stage3
```

Команда повторяема: уже созданные задания не дублируются. Она не создаёт
пользователей и не выдаёт права администратора.

## Контент трёх направлений этапа 6

После миграций полный демонстрационный набор этапа 6 создаётся командой:

```sh
cd ../tvoyvybor-frontend
docker compose run --rm backend python -m scripts.seed_stage6
```

Команда добавляет по четыре опубликованных сценария с одним `choice`-заданием
в направлениях Backend, Frontend и Analytics — всего 12 заданий. В каждом
задании есть сюжетный контекст, профессиональная ситуация и отдельные реакции
на правильный и неправильный ответ. Seed идемпотентен: он создаёт только
отсутствующие записи и прерывается, если одноимённое задание уже содержит
другой контент; данные пользователей и их прогресс не изменяются.

Игрок регистрируется, начинает опубликованный сценарий через
`PUT /scenarios/{id}/start`, затем отправляет
`POST /tasks/{id}/attempts` с JSON `{"request_id": "UUID", "answer": "GET"}`.
`request_id` создаётся клиентом один раз на логическую отправку и повторно
используется при сетевом повторе; тот же ID с другим содержимым даёт HTTP 409.
Ответ HTTP 201 содержит `id`, `task_id`, `is_correct`, `reaction` (`retry` или
`completed`), `explanation` и `scenario_state`. Неверный ответ можно повторить
без ограничения числа попыток. После первого верного ответа задание считается
выполненным; повторное выполнение с новым ID отклоняется с 409. Сценарий
завершается, когда верно выполнены все его опубликованные задания.

Каждая попытка сохраняется с серверным результатом, временем и событием
интереса. Неверный ответ даёт событие веса 0, первый верный ответ — событие
веса 1 по направлению сценария. `GET /interest-events` возвращает эти события;
`GET /interest-profile` — суммы весов по направлениям и число верно выполненных
заданий. `GET /recommendation` возвращает сохранённое направление с наибольшей
суммой и кратким объяснением либо `null` до первого верного ответа. При
равенстве выбирается направление с меньшим ID. `GET /achievements` показывает
достижение за первое верно выполненное задание. Все эти маршруты требуют JWT
и отдают только данные текущего пользователя. Попытка и её последствия
сохраняются одной транзакцией. XP и пропуск в этой версии не начисляются.

## Итоговый отчёт и управление контентом этапа 7

`GET /final-report` возвращает только факты текущего пользователя из
сохранённых `InterestEvent`: число попыток, число верно завершённых заданий,
до трёх направлений с причиной, наблюдения и следующий шаг. Это объяснимый
игровой отчёт, а не психологическая диагностика. Накопление баллов остаётся
детерминированным: первый верный ответ на задание добавляет событие
`task_completed` веса 1 для направления сценария; неверная попытка сохраняет
событие веса 0.

`GET /activity-profile` возвращает историю проб, явные впечатления об отдельных
действиях, объяснимые выводы и следующий шаг. Открытие станции, правильность и
время сами по себе не создают интерес. После принятого содержательного действия
`POST /quests/{id}/reflection` сохраняет добровольный ответ независимо от игрового
прогресса; `request_id` повторно используется при сетевом повторе. Две разные
пробы с положительным ответом дают повторившийся интерес, противоположные ответы —
смешанное впечатление. Старые общие реакции сохраняются без приписывания интереса
к действию. Миграция не требуется.

Администратор может просматривать, изменять и удалять черновые сценарии и
задания через `/admin/scenarios` и `/admin/tasks`, а также публиковать и снимать
с публикации существующими маршрутами `publish`/`unpublish`. Опубликованный или
уже использованный игроками контент менять и удалять нельзя: это сохраняет
воспроизводимость попыток, профиля и отчёта.

## Quest System

Миграция после `0005_onboarding_completed` добавляет таблицы квестов, не изменяя
исторические сценарии и попытки. После применения миграций демонстрационное
определение можно добавить командой `python -m scripts.seed_quests`. При наличии
направления `backend` квест связывается с ним; запускать seed следует после
наполнения направлений. Повторный запуск не изменяет существующий квест.

Авторизованный клиент может получить `GET /quests`, предложить задание через
`POST /quests/{id}/offer` с `{"npc_id":"boris"}`, принять его через
`POST /quests/{id}/accept`, отказаться через `POST /quests/{id}/abandon` и
выбрать отслеживаемое через `PUT /quests/tracked` с `{"quest_id":1}` или
`null`. Прогресс хранится отдельно для каждого пользователя.

`POST /game/interactions` принимает `request_id` (UUID), `event_type`,
`target_key` и `payload`. Повтор UUID с прежним содержимым возвращает прежний
результат, с другим — 409. Сервер проверяет последовательность целей и значения
параметров; `POST /game/backend-terminal` с `{"request_id":"UUID"}` доступен на этапе
диагностики и выдаёт исходное состояние терминала. Сервер сохраняет факт выдачи
и проверяет его до принятия исправления.

Для нового квеста добавьте опубликованное определение и упорядоченные цели с
устойчивыми идентификаторами NPC/объектов и правилами проверки, затем добавьте
соответствующие взаимодействия игрового мира. `validation_config` серверный и
в API не возвращается. Для новых типов действий, требующих особой проверки,
нужен отдельный обработчик; клиент не определяет успешность выполнения.


## Шесть интерактивных мини-игр

После миграций и создания направлений установите новый каталог:

```sh
python -m scripts.seed_minigames
```

Команда идемпотентна, публикует по две ситуации в Backend, Frontend и Analytics,
снимает с публикации `server-on-vacation`, сохраняет прежние определения,
пользователей и прогресс. Это замена игрового контента, а не очистка данных.
Старые API и таблицы остаются только для исторических клиентов и данных; новые
задания через `/game/interactions` завершить нельзя.

`GET /quests` возвращает `gameplay.kind` и персональный `gameplay.state`.
Телефон принимает задание через offer/accept; у одного наставника допускается
одно незавершённое профессиональное дело. Повторы безопасны, проверка
сериализована блокировкой пользователя. Ранее принятые параллельные дела
сохраняются и доступны через отслеживание. Игровые действия:
`POST /quests/{id}/actions` с `request_id` (UUID), `action` и `payload`
(`value`: строка до 4000 символов, `key`: строка до 40 символов). UUID один на
логическую попытку; его повтор возвращает первоначальный результат, другое
содержимое с тем же UUID отклоняется с 409. Состояние изолировано по игроку,
переходы и выдача наград сериализуются блокировкой пользователя в PostgreSQL.

Общие этапы: intro → interaction → mini-game → return → result → complete.
`intro-line` сохраняет следующую реплику (1–6), `intro-complete` разрешён
после последней. Старые снимки interaction и следующих этапов не сбрасываются.
Обсуждение сохраняет `debrief_line` через `dialogue-line`, key=debrief (1–2);
после последней реплики доступен report. Только
серверная проверка решения переводит в return; сдача наставнику и субъективная
реакция обязательны для complete. `quest_catalog.py` задаёт контент и общие
этапы, `quest_gameplay.py` — переходы, наблюдения и награды. Снимок состояния
и действия хранятся в существующих QuestEvent; миграция схемы не требуется.
Ошибочные гипотезы и проваленные проверки тоже сохраняются.

## Сюжетное вступление и финал

Миграция `0006_story_progress` добавляет серверные флаги `intro_completed` и
`main_story_completed`; для существующих аккаунтов вступление переносится из
`onboarding_completed`. `GET /game/state` возвращает сюжетные флаги и открытие
финального разговора. `PUT /game/intro-complete` сохраняет завершение
вступления. `PUT /game/final-quest/complete` доступен только после завершения
всех опубликованных мини-игр движка 2 в Backend, Frontend и Analytics; он
идемпотентно отмечает сюжет завершённым и выдаёт достижение «Теперь хотя бы не
наугад».

Python проверяется ограниченным AST-интерпретатором `quest_python.py`: без
exec/eval, импортов, произвольных вызовов и доступа к атрибутам. Доступны списки,
числа, арифметика, присваивания, for/if/return, sum/len/append и списковое включение.
Каждый тест ограничен бюджетом операций. Подсказки не отправляют данные наружу.

Профиль хранит добровольное начало, завершение, попытки, выборы, подсказки,
просмотр/использование примера, дополнительное исследование, реакцию и успех.
`engage` раз в 30 секунд видимого интерфейса уточняет активное время по серверным
часам; паузы между событиями ограничены 90 секундами. Это приблизительное время
участия, а не поведенческая диагностика. Качество решения и использование помощи
не уменьшают интерес: основной сигнал — реакция и желание исследовать дальше.
Награды выдаются в существующее приложение достижений; итоговый отчёт и
рекомендация используют новый источник `quest-experience` при его наличии.

Проверки: `pytest -q tests/test_minigames.py` и общий набор из раздела выше.

Редактирование `property`, `draft` и `draft-repair` не увеличивает число
попыток. `failed_checks` отделён от проверок. Responsive проверяет геометрию
ограниченного макета на трёх ширинах; UX проверяет понятные признаки текста
и возвращает последовательный `user_trace` до первого затруднения.
После успеха инструменты доступны: `explore` принимает конкретную проверку
через key/value, сохраняет её результат один раз на набор параметров и
не отменяет основной успех.

### Отложенное дело и новый проход

`intro-defer` на реплике 4 сохраняет временный отказ без продвижения целей;
`intro-resume` возвращает к согласию на реплике 5. Полный отказ через
`/quests/{id}/abandon` добавляет событие `minigame_reset` и очищает цели только
текущего прохода. Старые события сохраняются; новый accept начинает intro с нуля.

`debrief-answer` для code принимает yes/partly/help/silence и сохраняет ветку
ответа. Интервью поддерживает свободный порядок 13 вопросов, хранит историю
`interview_history`. Действие `compose` принимает JSON в payload.value с полями
problem, automation, data, delivery: сервер проверяет собранный процесс и наличие
наблюдений. Прежние proposal/criteria доступны для совместимости старых клиентов.

`assistant-question` в code принимает payload.key только из подготовленного
списка: none, average, empty, zero, logic, why-zero, sum, tests, loop, function,
python, javascript, example. Вопросы сохраняются в assistant_questions; example
разрешает взять показанный пример в редактор. Старый hint сохраняет совместимость.
